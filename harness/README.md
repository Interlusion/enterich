# Improvement pipeline

The scripts, schemas and rubrics of the improvement pipeline: agents between deterministic stages, on `auto/` branches only. Why and the rules: [ADR-008](../docs/arc42/adr/ADR-008-improvement-pipeline.md).

## The tests lens

A run lives in `runs/<date>-tests/`.

1. **Inventory:** `uv run python harness/inventory.py harness/runs/<date>-tests` writes the specs' requirements with their Definition of Done items (`requirements.jsonl`), the tests with the requirement IDs they cite (`tests.jsonl`), and the counts (`inventory.json`).
2. **Mutation:** `uv run --group harness python harness/mutation.py harness/runs/<date>-tests [--fresh]` runs mutmut over `src/enterich/` against the unit and integration tests (`[tool.mutmut]` in `pyproject.toml`) and writes the surviving mutants with their diffs (`survivors.jsonl`) and the counts per module (`mutation.json`). A survivor a script can judge gets a `filter` and isn't surveyed: one that changes only the type text of a `cast()`, or only the wording of an error that is raised or of a log message. Where a string goes is read from the function's source, so a name, a format, a header or a result's text that reads like prose is left to the agents. CPU only, about half an hour on 8 cores; mutmut keeps its state in `mutants/`, so a second run checks only what changed.
3. **Survey and verify:** the Workflow `improve-tests` (`.claude/workflows/improve-tests.js`), run from Claude Code by its file path, not its name (the name can give an older copy), with the run directory and the records of `patterns.jsonl` among its arguments. Its agents read the run's files and return findings, each with a verdict from another agent, which also names the finding's pattern if it has one and the test files its fix will change; `uv run python harness/record.py harness/runs/<date>-tests <the workflow's output file>` writes them to `findings.jsonl`, those not verified to `unverified.jsonl`, in place of what the surveys that answered found before (the sweep's findings, and those of a survey that didn't answer this time, stay; there is one record per key, the first, naming the others that made it in `also`, so a finding the sweep holds isn't recorded again), and the workflow's agents and tokens to `workflows.jsonl`. Before it writes anything, it scans the whole result with the gate's gitleaks; a result with a secret, real or made up, is written nowhere, and the agent is asked again without it, since the records are committed by hand, past the gate. **The sweep:** a survey misses things, so `uv run python harness/sweep.py harness/runs/<date>-tests` then looks for each confirmed mutant gap's class in every survivor. It takes the project's own functions and classes whose call or definition the finding's mutants change, finds the survivors left to agents that change the same one and that no finding names, and writes them by function to `sweep.jsonl`. It follows the innermost such call in a line, so `str(own(…))` counts as `own`, and a call on an object counts only when the object is one of the project's modules, `self`, `cls` or one of its classes. A call of Python or a library, such as a dict's `get` or `tomllib.load`, isn't followed, even where the project defines a function of the same name. The Workflow `improve-tests` run again with `sweep` (the records of `sweep.jsonl`) instead of `specs` and `moduleBatches` verifies each candidate, and `record.py` adds the verdicts to `findings.jsonl` and `unverified.jsonl`, so triage counts them with the survey's. A key judged before keeps its verdict. A candidate whose verifier didn't run waits in `unverified.jsonl` and comes again with the next sweep; once judged, it waits no longer. In the fourth run it would have found the 17 survivors of the duplicate texts that the survey missed, in five places.
4. **Triage:** `uv run python harness/triage.py harness/runs/<date>-tests` checks every record, sets aside what `suppressions.jsonl` lists, sorts the confirmed findings into fix, proposal and dropped, and writes `report.md`.

Triage also writes the fix stage's input. `fixes.jsonl` holds each fix with its key, its branch's slug and its mutants' diffs. `ratchets.jsonl` holds a ratchet for each pattern that three or more fixes share across at least two files, with its findings' keys; those fixes name it in `ratchet`.

5. **Plan:** `uv run python harness/plan.py harness/runs/<date>-tests` groups the fixes so that no two branches plan the same test file, and writes `groups.json`: per branch its test files, its ratchets and its fixes. Fixes share a branch when their verdicts name a test file in common or when they follow one ratchet; a fix whose verdict names no file stays with its survey. Run again after the fix stage, it plans what is left: a fix with an outcome in `outcomes.jsonl` isn't planned, a ratchet with one isn't run again, and the findings of a ratchet no review accepted are planned as fixes of their own, on the branch of their test file. A fix whose agent didn't answer has no outcome. A fix whose agent found its test belongs in another branch's file ("elsewhere", the file in its notes) is planned once more in that file, and one its agent found already closed ("refuted") is planned once more if a fix on its branch was rejected, as the test that closed it may be dropped. A test file that an accepted fix changed stays with that fix's branch, which holds its commits: the fixes naming it go there, together with the others of that branch, and a group with files of two such branches names the second in `also`, to be merged first. A branch that holds nothing a review accepted isn't kept, so the findings of a rejected ratchet don't land beside its test. The plan names each branch it plans for that holds commits no review accepted: drop them (step 7) before the fix stage, or the next agents build on them. A fix of an accepted ratchet that is planned later carries `ratchet_done`, and its agent is told the generic test is there.
6. **Fix:** the Workflow `improve-tests-fix` (`.claude/workflows/improve-tests-fix.js`), run by its file path, with the run directory, the base branch (`origin/main` unless given, after a `git fetch`), the commit holding the run, the session's commit trailers and the run's `groups.json` as its arguments; each agent reads its record from the run. Each group gets its branch, and the groups run side by side. A group's ratchets go first: each agent writes one generic test for its pattern wherever it can occur, shows it red against its findings, and is reviewed before they start; a finding its test already closes gets no test of its own. If no review accepts a ratchet, its findings are skipped; planning the run again (step 5) gives each a test of its own. The findings' agents run in turn, each in a worktree of its own, detached: it writes the test, shows it red against the mutant or a break, commits it (`test:`, then a `fix:` only if the code was wrong), and moves the branch to its commits. An agent whose test belongs in an existing test file that isn't among its branch's commits nothing and says so (`elsewhere`). Another agent redoes the red check and reviews each finding's commits. Nothing is pushed. `harness/record.py`, as in step 3, adds the result's `outcomes`, one record per fix with the fix agent's answer and the review's, to `outcomes.jsonl`; it refuses a second, different outcome for a fix that has one, unless its agent hadn't answered or the plan handed the fix out once more; that second outcome says in `replaced` what it replaced, and stays.
7. **Outcomes:** `uv run python harness/outcomes.py harness/runs/<date>-tests` checks every record against `fixes.jsonl` and `ratchets.jsonl`, gives each fix its state (accepted, rejected, unreviewed, refuted, proposal, elsewhere or failed), and writes `outcomes.json`: the counts, the fixes without an outcome, per branch the commits of the fixes no review accepted, which are dropped from their branch by hand, and per branch the commits of the accepted ones, the only commits the gate lets through.
8. **Gate:** `E2E_ERPNEXT_URL=… uv run python harness/gate.py harness/runs/<date>-tests auto/tests-… [--push]` compares each branch with `origin/main` (`--base`), fetched first, so a local `main` behind it can't count merged commits as the branch's own. It reads each branch once, at one commit, which is what it checks, records and pushes, wherever the branch moves meanwhile. It refuses a branch that isn't `auto/`, doesn't start with a `test:`, has a change that isn't right after its `test:`, has a `test:` commit that changes more than tests, holds a commit that is no accepted fix's in `outcomes.json` (by hash, or, once a rejected commit before it was dropped, by a diff that is the same to the letter, `git patch-id --verbatim`), changes a test file `groups.json` plans for another branch, changes code or `CHANGELOG.md` that a branch which passed before it in the same call changes (the second is gated again once the first is merged; a branch that failed holds nothing back). A branch held back so is rebased onto the new `main`; where the rebase resolved a conflict, a commit's diff is no longer the one a review accepted, so the Workflow `improve-tests-fix` runs with `rebased` (each fix's record in `outcomes.jsonl` and its rebased commits) instead of `groups`: only a review of the rebased commits, the resolution included. `record.py` lets its outcome take the accepted one's place, only for the commits recorded, and keeps the earlier commits and review under `rebased`; then `outcomes.py` runs again, or changes anything but tests, code under `src/enterich/` and `CHANGELOG.md`, or among those what ADR-008 forbids, what configures a check or what instructs an agent, wherever it lies (a file moved away counts at its old place, and a path is read as it is, whatever its name holds). It scans the branch's commits and their messages for secrets with the gitleaks CI pins (`.github/gitleaks/`; CI scans only pull requests and pushes to `main`, and the pipeline pushes on its own), runs every check in a worktree of that commit, the end-to-end tests included (the site: `scripts/erpnext-site.sh up`). The tests fail if any was skipped, expected to fail or left out, or if a test `main` had where the branch left it no longer runs and passes in as many cases: removed, renamed, moved to a file pytest doesn't collect, or with a case taken away (only the operator removes a test). It writes `gates.jsonl`. With `--bundle`, the branches that passed and change only tests go in turn on `main` as one branch named after the run (`auto/<date>-tests`), checked like any branch and pushed in their place, so the operator merges one pull request for them and one for each branch that changes code; if they conflict or the bundle fails, each goes on its own. With `--push`, it pushes the branches that passed, and records a push that failed as not pushed; a branch that passed earlier at the same commit is pushed without a second run of the checks, so run the gate first without `--push` and then with it, and never push an `auto/` branch by hand. The operator opens and merges their pull requests.
9. **Cleanup:** `uv run python harness/cleanup.py [--finished] [--remove]` lists the fix workflow's worktrees under `.claude/worktrees/` that are done with, and the branches made for them; with `--remove` it removes them. A worktree is done with when it isn't locked, holds no uncommitted change and its commits are on an `auto/` branch; one without commits only with `--finished`, once the workflow has ended. A worktree whose folder is gone is taken off git's list under the same rule, so a crashed agent's commits on no `auto/` branch stay reachable; one git refuses to remove, as it changed since the survey, keeps its branch, and the rest go on. No other worktree of the repository is touched. It can run while the fix stage does: Claude Code locks an agent's worktree for as long as the agent runs.

## The security lens

A run lives in `runs/<date>-security/`; a run's lens is in its directory's name. Triage, the plan, the fix stage and the gate are the tests lens's, with the fix stage's prompts worded for its findings. The first run surveyed every promise; a run after it surveys what changed since the last run's records, and the lens rests once a run confirms no breach in Enterich or its guides, and while neither `src/` nor the configuration guide has changed.

1. **Inventory:** `uv run python harness/surface.py harness/runs/<date>-security` writes each promise with its requirements, their Definition of Done items and the tests citing them (`promises.jsonl`), and what the promises are kept on (`surface.json`): the published tools with their text inputs without a bound, every request Enterich sends ERPNext and where the code calls the client, every log call, the settings and every silenced security rule of the linter. The promises are the lens's vocabulary, `promises.jsonl` here: what `SECURITY.md` names as in scope and the rules of `AGENTS.md` about what Enterich may do, each by a text of its source. A scope line of the policy without exactly one promise, or a promise whose source no longer holds its text, stops the inventory. With `--since <commit>`, the commit that holds the last run's records, `surface.json` also lists under `since` the files changed after it and the promises they touch: a change to a promise's source or under one of its start paths.
2. **Survey and verify:** the workflow `improve-security` (`.claude/workflows/improve-security.js`) with `{run, promises, patterns}`, and in a run after the first with `since` and the promises `surface.json` names under it, so each survey begins with the diff since that commit: one agent per promise looks for a way to break it and for the places no test would notice breaking, and one skeptic per finding tries to refute it. A finding is a **breach** (the promise can be broken), confirmed only as reproduced against the tests' fakes or the local end-to-end site, or **unproven** (the promise holds as far as read, but no test would notice it breaking). `harness/record.py` writes the result as for the tests lens.
3. **Triage:** `uv run python harness/triage.py harness/runs/<date>-security`, as for the tests lens. A security finding's key is its kind, promise and location, and its fix branches are `auto/security-…`.

Findings are committed and pushed like any other: the operator decided that a breach found here is fixed in the open.

## The docs lens

A run lives in `runs/<date>-docs/`. Triage and the plan are the tests lens's; the deterministic part of the lens is in CI (`tests/repo/test_docs.py` and the checks it names), so the agents read only what a script can't compare. The first run surveyed every record; a run after it surveys the records touched since the last run's records, and the lens rests while nothing they read has changed.

1. **Inventory:** `uv run python harness/documents.py harness/runs/<date>-docs [--since <commit>]` writes the records the lens surveys (`documents.jsonl`). The records are the lens's vocabulary, `documents.jsonl` here: each names its documents, what they are read against and what the survey asks; every document that says what Enterich does (`SCOPE` in the script) is in exactly one record, one surveyed or one left out with its reason (`out`). A document in no record or in two, a path that doesn't exist or a record that doesn't say what it asks stops the inventory. With `--since`, `since.json` names the files changed after that commit and the records they touch: a change to a document of theirs or under what they are read against.
2. **Survey and verify:** the workflow `improve-docs` (`.claude/workflows/improve-docs.js`) with `{run, documents, patterns}`, and in a run after the first with `since` and the records `since.json` names. One agent per record looks for a **drift**: a document saying what the code doesn't do, naming what no longer exists, or leaving out what leads a reader wrong; it says which side is wrong (where a spec states the behaviour, the code; else the document). One skeptic per finding tries to refute it and confirms it only with both sides quoted, or run where only running shows the code's side. `harness/record.py` writes the result as for the other lenses.
3. **Triage:** `uv run python harness/triage.py harness/runs/<date>-docs`. A drift's key is its kind, record and location (`drift:configuration-guide:docs/guides/configuration.md:ENTERICH_PORT`).
4. **Fix:** a drift with the code wrong goes through the tests lens's fix stage and gate. One with the document wrong changes a guide, `docs/arc42/README.md` or `README.md`, which the gate doesn't let through, or a tool's description and with it the tool-list snapshot, which ADR-008 keeps to the operator: the first run's are fixed by hand, and its retrospective says whether the fix stage should take them.

## Budget

When the turn that starts a workflow has a token target, the workflows stop before it is spent: no verifier and no fix starts once less than the `reserve` argument is left (50,000 tokens unless given). Findings not verified are returned unverified, and fixes not started count as missing in `outcomes.json`; running the workflow again takes them up. Without a target nothing stops a run but its universe.

## Patterns

`patterns.jsonl` holds the operator's classes of finding, one JSON object per line: `{"pattern": "<slug>", "means": "…"}`. A verdict names one of them or none; triage refuses any other, so an earlier run whose verdicts name a pattern since removed or renamed can't be sorted again. A class nobody has named yet shows only in reading a run's findings: add it here, and the next run's verdicts can name it.

## Suppressions

`suppressions.jsonl` holds what the operator decided not to act on now, one JSON object per line: `{"key": "<finding key>", "reason": "…"}`, and `"backlog": "item-NNN-….md"` when a backlog item will take it up. Triage counts a finding with a backlog item as tracked while the item's file is in `docs/backlog/`; once it is archived, the finding comes back. One without stays suppressed.

Triage gives each finding its key: a mutant gap's lowest mutant id (`mutant-gap:enterich.shapes.x_page__mutmut_9`), since one function can have several gaps; else the kind and location (`dod-gap:req-001-core.md#REQ-001-PRS-F014 item 3`, `weak-test:tests/…::test_…`). A key outlasts a rerun as long as the code or item it names doesn't change; triage refuses two records with one key.
